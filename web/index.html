Real-time · Realtime Lab

Push one byte to ten million phones.

A real-time system is a distributed routing problem, not a connection problem. Holding a million WebSockets is the easy 20%; the hard part is "given a message for user X, which of my 500 gateway nodes holds X's socket?" — and surviving the reconnect storm when you deploy. This lab draws the registry, the backplane, the fan-out, and the recovery.

Pick a lesson in the sidebar. The throughline of every war story: the hard part of real-time is the correlated-failure recovery path, not the happy path. A deploy doesn't fail one connection — it fails millions simultaneously, and the recovery is itself the load spike.

Transports — decide with a trigger, don't enumerate

Every transport answers one question: how does the server reach a client that didn't just ask for anything? The interview-winning move is a decision tree, not a favorite — pick the workload and read off the answer with its reason.

The proof: WebSocket is the default for chat because it's bidirectional and latency-sensitive both ways (typing/receipts flow client→server constantly). But SSE is criminally underused for push-dominant feeds — reconnect + replay come free. Say "SSE here because the traffic is 95% server→client" and you've out-signaled "we use WebSockets." Long-poll is the universal fallback; MQTT is the low-end-mobile answer.

The two-hop problem — which node holds user X?

A WebSocket pins a user to one gateway node. When Y sends a message to X, Y's node has no idea where X lives. The load balancer's stickiness does not solve this — you need a separate connection registry (user→node) plus a pub/sub backplane. Conflating the two is the #1 disqualifier.

Send a message and watch it hop the backplane.

The proof: the message doesn't go straight to Bob — it looks up Bob in the registry (→ gw3), publishes to gw3's channel on the backplane, and gw3 pushes it down Bob's socket. If Bob's node crashed, the TTL registry still points at the dead node for a few seconds (the dead-node window) and the message is dropped — but at-least-once retry + Bob's cursor resync catches the gap on reconnect, which is why you accept the window instead of paying for consensus.

C10M — connections are a memory problem

Holding millions of connections is memory-bound, not CPU-bound: each idle WebSocket costs tens of KB. Thread-per-connection is dead (10k threads = GBs of stack) — one event loop multiplexes them all. And you plan capacity for the failure case: a dead node's connections stampede onto the survivors.

The proof: RAM ÷ per-conn state gives a theoretical max, but you run well below it — a lean cap that leaves room for message-processing CPU, GC pauses, and (the staff distinction) failover absorption. Derive the node count from memory + headroom; never quote a memorized "2M/node." Thread-per-conn memory explodes linearly at 1 MB/thread; the event loop stays flat.

Ordering — server seqNo, never client clocks

Networks reorder messages. You need messages in a conversation to appear in the same order for everyone — not a global order (impossibly expensive), just per-conversation. The mechanism: a server-assigned seqNo scoped to the conversation (the partition key) + a client reorder buffer that holds gaps until they fill.

The proof: ordering by the server seqNo, a gap (a missing seq) is held in the reorder buffer until the missing message arrives — the conversation renders correctly for everyone. Ordering by client clocks, skew and malicious clients scramble it: "nvm" renders before "are you ok?". The server seqNo is truth; client time is only a display/dedup hint.

Receipts — sent is persistence, not delivery

The famous ticks: sent (durably stored — a server fact), delivered (reached the device — a client ACK), read (opened — a client signal). The non-obvious staff point: "sent" must be backed by persistence, not fan-out success, or a delivery hiccup looks like a send failure.

—

The proof: the single grey tick fires the instant the server persists and assigns a seqNo — before Bob is even reached — because "sent" means durably stored. Double-grey = delivered (Bob's device ACKed), double-blue = read. And you collapse receipts ("read up to seqNo N" in one message): in a 50-person group, naive per-message read receipts are 50× the message traffic.

Group fan-out — write vs read, the threshold

Where do you pay the fan-out cost? Fan-out-on-write copies each message into every recipient's inbox (fast reads, write amplification = group size). Fan-out-on-read stores it once in a shared log (cheap writes, reads do the work). The staff answer is a threshold hybrid — and the crossover is where write-amp cost meets read-query cost.

The proof: below ~a few hundred members, fan-out-on-write wins — materialize per-inbox copies for O(1) reads. Above it, one message to a 100k-member group = 100k inbox writes (the celebrity problem, ~50k writes/sec for one busy group), so you store it once in a shared log and fan out the live push only to currently-online members — the offline majority syncs from the log on reconnect.

Push — a wake-up nudge, not delivery

When the recipient has no live socket, you hand the message to APNs/FCM to wake the device. Three staff details: the online↔push race (dedup by msgId), "sent to APNs" ≠ "delivered" (the inbox sync on open is the real delivery), and notification collapse (one buzz, not five).

The proof: online → the socket delivers directly. Offline → APNs/FCM sends a contentless nudge; the message waits in the durable inbox and is really delivered by the sync on app-open. If a message arrives just as the app backgrounds, it goes to both socket and push — the client dedups by msgId. Three pushes collapse to one "3 messages" buzz. A 410 prunes the dead token.

E2E — the server becomes a blind relay

With end-to-end encryption (the Signal Protocol), only the clients hold keys — the server relays ciphertext it cannot read. X3DH agrees a key even while the recipient is offline; the double ratchet evolves a key per message (forward secrecy + self-healing). The staff point: E2E reshapes the architecture, it isn't "add encryption."

—

what the server sees

—

The proof: Alice and Bob derive the same shared secret via Diffie-Hellman without Bob online; each message ratchets a fresh key, so stealing today's key can't decrypt past messages (forward secrecy). The server only ever holds ciphertext — which forces the architecture: no server-side search or moderation, push carries no preview, multi-device must encrypt per-device, and groups need Sender Keys for O(1) fan-out.

Presence — a fan-out amplification problem

"Online / last-seen / typing" is where naive chat designs die. It's soft state (Redis TTL, not the message DB), and the killer is fan-out: one flip notifies everyone watching. A flapping mobile user in a big group is a self-inflicted DDoS. The cheapest update is the one you never send.

The proof: naive presence = flaps × watchers, and it explodes. Subscribe-on-view (watch the ~20 contacts on screen, not all 500) + debounce (wait 30–60 s before broadcasting "offline" to absorb mobile flapping) + aggregate ("1.2k online" for huge groups) cut it by orders of magnitude. Presence is eventually consistent by design — WhatsApp's slightly-stale "last seen" is the correct cost decision, not a bug.

Offline sync — fetch-since a cursor, not replay-the-queue

A phone in a tunnel for 3 days reconnects. Wrong: keep a durable per-user queue of every message. Right: messages live in the shared conversation log with monotonic seqNos; the client remembers its cursor (lastRead) and asks "give me everything after N." One primitive solves offline catch-up, reconnect gap-fill, and multi-device read-sync.

hours offline6h
—

The proof: the gap between the client's cursor and the log head is the queue — no separate per-user queue structure needed. Reconnect fetches just that delta (seqNo > lastRead), so a 3-second or 3-day gap works identically and is idempotent (ask twice, same answer). The same cursor replicated across a user's devices keeps read-state in sync — one primitive, three problems.

Backpressure — one slow client takes down a node

If the server pushes faster than a slow 2G client can drain, its send buffer grows. Unbounded buffering = OOM, and the GC pressure stalls the event loop so every connection on that node degrades. The fix: bound every send buffer and drop the slow consumer — node availability beats one degraded client, and they re-sync from a cursor anyway.

—
node memory (sum of send buffers) per tick · red line = OOM

The proof: unbounded → the slow client's buffer grows every tick, node memory climbs to OOM, and the healthy connections degrade too (one slow client, whole-node outage). Bound + drop caps each buffer and closes the slow consumer when it overflows → node memory stays flat and the healthy connections are untouched. Coalesce latest-wins for presence/typing; only spill to a durable queue for messages you truly can't lose.

The reconnect storm — deploy without dropping 2M sockets

The signature staff question. A naive deploy kills all sockets at once → they all reconnect in the same instant → registry write storm + auth stampede + presence flap → cascading outage. The fix: drain slowly, reconnect with jitter, size survivors with headroom, and resume from a cursor.

jitter window10
—
reconnects per tick · red line = survivor accept capacity

The proof: naive → all 2M reconnect in one tick, a spike far past the survivors' accept capacity → overload. Slow drain over a long window + jittered staggered reconnect flattens it to a plateau under capacity; a wider jitter window spreads it further. Resume from a cursor so each reconnect is cheap. And run continuous connection rotation in steady state so the recovery path is always warm — a deploy is just a louder version of normal.
